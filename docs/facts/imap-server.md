# IMAP server

Binary: `fakeimap`, at the checkout root. `make` runs `go test ./...` and then `go build -o fakeimap .`. `make clean` deletes that binary.

Run: `fakeimap <config.json>`. The one argument is the config path. Paths inside the config are relative to the process working directory, not to the config file.

Before accept, the process writes one JSON object to stdout and flushes it. The object has `listen` when a cleartext listener is bound, `implicit_tls_listen` when an implicit-TLS listener is bound, `control` when the control socket is bound, `smtp` when a cleartext SMTP listener is bound, `smtp_listeners` for every cleartext SMTP bind, `smtp_tls` when an implicit SMTP TLS listener is bound, `smtp_tls_listeners` for every implicit SMTP TLS bind, `jmap` when the JMAP listener is bound, `jmap_tls` when the JMAP TLS listener is bound, and `sieve` when the ManageSieve listener is bound. `smtp` is the first cleartext SMTP bind. `smtp_tls` is the first implicit SMTP TLS bind. A configured port of `0` is the bound ephemeral port.

## Config keys

- `listen` — `host:port` cleartext listener. Empty or omitted: no cleartext listener. Port `0`: ephemeral.
- `implicit_tls_listen` — `host:port` implicit TLS listener. Empty or omitted: no implicit-TLS listener. Port `0`: ephemeral.
- `cert_file` — PEM certificate for `STARTTLS` and implicit TLS.
- `key_file` — PEM private key matching `cert_file`. Not part of the repo; tests generate one.
- `client_ca_file` — PEM trust anchors for an optional client certificate. Used when the personality lists `AUTH=EXTERNAL` and a server certificate is loaded. Empty or omitted: a client certificate is requested only if `AUTH=EXTERNAL` is listed, and it is not verified. A connection without a client certificate still completes the handshake.
- `log_path` — file to append. Empty or omitted: no log file is created.
- `personality` — personality JSON file.
- `dataset` — dataset directory. The directory contains `dataset.json`.
- `control` — filesystem path of the mode-0600 Unix control socket. Empty or omitted: no socket.
- `smtp_listen` — one cleartext SMTP listener, or an array of them. A string is `host:port`. An array entry is a `host:port` string or an object `{"addr":"host:port","dsn":true}`. Empty, omitted, or `""` binds nothing. Port `0` is ephemeral. `0.0.0.0` is a valid host. `dsn` defaults to false. See SMTP below.
- `smtp_dsn` — optional, with the string form of `smtp_listen`. True turns `dsn` on for that one listener. With any other number of listeners it is a config error.
- `smtp_tls_listen` — a `host:port` string, or an array of those strings or the same objects as `smtp_listen`. TLS starts at the first byte. Empty or omitted: not bound. Port `0`: ephemeral. It uses `cert_file` and `key_file`. Setting it without them is a config error. An implicit TLS session does not list `STARTTLS`.
- `smtp_auth_required` — default true. False omits `AUTH` and accepts mail with no AUTH, and does not deliver it to an IMAP mailbox. See SMTP below.
- `smtp_size` — the EHLO `SIZE` limit in octets. Omitted or `0` means `10000000`. A negative value is a config error.
- `jmap_listen` — `host:port` cleartext HTTP JMAP listener. Empty or omitted: no JMAP listener. Port `0`: ephemeral. The port speaks cleartext. It does not speak TLS. It does not satisfy the requirement for an IMAP listener.
- `jmap_tls_listen` — `host:port` JMAP listener with TLS from the first byte. Empty or omitted: not bound. Port `0`: ephemeral. It uses the certificate already loaded from `cert_file` and `key_file`, and the same routes as `jmap_listen`. The cleartext listener is unchanged. It does not satisfy the requirement for an IMAP listener. Setting it without `cert_file` and `key_file` is a config error.
- `sieve_listen` — `host:port` ManageSieve listener. Empty or omitted: no ManageSieve listener. Port `0`: ephemeral. It does not satisfy the requirement for an IMAP listener. Scripts are stored in memory, per dataset account, and are not executed. `CHECKSCRIPT` and `PUTSCRIPT` accept only the small command list below.
- `oauth_listen` — `host:port` cleartext HTTP OAuth listener. Empty or omitted: no OAuth listener. Port `0`: ephemeral. It does not replace the IMAP listener and does not satisfy the required-listener check.
- `oauth_tls_listen` — `host:port` OAuth listener with TLS from the first byte. Empty or omitted: not bound. It uses the same certificate as the other TLS listeners. Setting it without `cert_file` and `key_file` is a config error. `reload-cert` applies to the next handshake.
- `oauth_access_seconds`, `oauth_refresh_seconds`, `oauth_code_seconds` — lifetimes. Defaults are 3600, 86400, and 60.
- `oauth_rotate_refresh` — default true. True rotates the refresh token. False omits `refresh_token` on refresh and the previous one still works.
- `oauth_clients` — optional clients, each with `id`, `secret`, and `redirect_uris`. An empty list keeps the built-in public client `test-client` with redirect `com.example.app:/oauth2redirect`. A listed `test-client` overrides that built-in. A list that omits `test-client` still keeps it.

At least one listener is required. Implicit TLS, `jmap_tls_listen`, `smtp_tls_listen`, and `oauth_tls_listen` require `cert_file` and `key_file`. `STARTTLS` is offered on a cleartext connection only when a certificate is loaded and TLS has not started. `smtp_listen`, `smtp_tls_listen`, `jmap_listen`, `jmap_tls_listen`, `sieve_listen`, `oauth_listen`, and `oauth_tls_listen` do not satisfy that requirement.

## JMAP

`jmap_listen` stays cleartext HTTP. `jmap_tls_listen`, when set, is a separate listener that speaks TLS from the first byte and serves the same routes. Session URLs stay paths on both.

`GET /.well-known/jmap` with HTTP Basic for a dataset account returns the session. `Authorization: Bearer` is accepted on the API, upload, download, and event source. A bad bearer is 401 with both `WWW-Authenticate: Bearer realm="jmap"` and `WWW-Authenticate: Basic realm="jmap"`. A bad Basic password stays Basic-only. On `stalwart`, `stalwart-0155`, `stalwart-01625`, `stalwart-dev`, and `stalwart-oauth`, identified by the basename of the personality path, `GET /.well-known/jmap` is 307 to `/jmap/session`. Unauthenticated `GET /jmap/session` on those names is 200 with `username` `""`, `accounts` `{}`, `primaryAccounts` `{}`, and the same capability and URL fields as an authenticated session, including `state`. An authenticated session returns that user's document. On every other personality both paths stay 401 without credentials. `POST /jmap`, upload, download, and event-source stay 401 without credentials on every personality. A missing or wrong password is 401. `capabilities` and that account's `accountCapabilities` are `urn:ietf:params:jmap:core`, `urn:ietf:params:jmap:mail`, and `urn:ietf:params:jmap:submission`. `primaryAccounts` points each of those at that account. `username` is the account name. `apiUrl` is `/jmap/`. `downloadUrl` is `/jmap/download/{accountId}/{blobId}/{name}?accept={type}`. `uploadUrl` is `/jmap/upload/{accountId}/`. `eventSourceUrl` is `/jmap/eventsource/?types={types}&closeafter={closeafter}&ping={ping}`. Those are path-only. `state` is a string and changes when the store changes, including an IMAP append, flag change, or expunge, and a JMAP import, update, or destroy.

One JMAP account per dataset user. The account id is the username. Mailbox ids and email ids are assigned for the life of the process and are not IMAP UIDs. `POST /jmap/upload/{accountId}/` with a non-empty body stores those bytes and returns JSON `accountId`, `blobId`, `type`, and `size` with status 201. An empty body is 400. A missing or wrong password is 401. An account id other than the authenticated user is 404. `GET` of the download URL returns an uploaded blob, or the RFC822 bytes of an `Email/get` `blobId`. An unknown blob id is 404. `GET` of `eventSourceUrl`, with the placeholders filled and HTTP Basic, returns 200 and `Content-Type: text/event-stream` before the store changes, and the body stays open. A missing or wrong password is 401. When `types` includes `Email`, the next store change writes one event, `event: state`, whose data is a JSON object with `changed` set to that account id and `Email` set to the new state string. That string is the state `Email/changes` would report. The connection closes after that event when `closeafter` is `state`. A positive `ping` writes a line `: ping` and a blank line at that interval while the stream waits. `types` that does not include `Email` sends no state event.

`Mailbox/get` returns `id`, `name`, `parentId`, `role`, `sortOrder`, `totalEmails`, and `unreadEmails`. `INBOX` has role `inbox`. A special-use flag maps to the matching role (`all`, `archive`, `drafts`, `flagged`, `junk`, `sent`, `trash`). `totalEmails` and `unreadEmails` are IMAP `STATUS` `MESSAGES` and `UNSEEN`. `Mailbox/query` accepts a `parentId` filter, including null, and `AND`, `OR`, or `NOT` of those filters. Sort properties are `sortOrder` and `name`.

`Email/query` accepts `filter.inMailbox`, a `receivedAt` sort, `limit`, `position`, and `calculateTotal`. A filter other than `inMailbox`, or a sort other than `receivedAt`, is `invalidArguments`. `Email/get` returns `id`, `blobId`, `threadId`, `mailboxIds`, `keywords`, `size`, `receivedAt`, `sentAt`, `subject`, `from`, `to`, `preview`, `hasAttachment`, `bodyStructure`, `headers`, and `bodyValues`. `preview` is the IMAP `PREVIEW` string, including the 256-character cap and the first `text/plain` part. An empty snippet is `""`. Keywords are `$seen`, `$flagged`, `$answered`, and `$draft` for those IMAP flags. `headers` are `{name, value}` objects. `bodyValues` follows `fetchAllBodyValues`, `fetchTextBodyValues`, `fetchHTMLBodyValues`, and `maxBodyValueBytes`, and sets `isTruncated` when the value is cut. A method argument whose name starts with `#` is a result reference to an earlier call in the same request.

`Email/import` of an uploaded blob id into exactly one mailbox appends it there, returns the new email id under `created`, and an IMAP `IDLE` on that mailbox receives `EXISTS`. The keywords `$seen`, `$flagged`, `$answered`, and `$draft` become those IMAP flags. Zero mailboxes, more than one mailbox, an unknown blob id, or an unknown mailbox id is `invalidArguments` and stores nothing. `Email/set` `destroy` removes those ids from every mailbox they are in and lists them in `destroyed`. An id that was not there is listed in `notFound`, and the others are still removed. `create` is `invalidArguments` and changes nothing, including when `update` or `destroy` is also present. `update` patches `keywords/$seen`, `keywords/$flagged`, `keywords/$answered`, and `keywords/$draft` to `true` or `null`, which sets or clears that IMAP flag, and `mailboxIds/<id>` to `true` or `null`, which adds or removes that mailbox. One email id may be in more than one mailbox. Adding a mailbox appends the message there so IMAP `IDLE` sees `EXISTS`. Removing one expunges it there so `IDLE` sees `EXPUNGE`. A successful id is listed in `updated`. Removing the last mailbox, an unknown mailbox id, any other keyword, or a value other than `true` or `null` lists that id in `notUpdated` with type `invalidProperties` and does not change it. An unknown email id is `notUpdated` with type `notFound`. Other ids in the same `update` still change. A call with `update` and `destroy` applies both. `Email/changes` with `sinceState` returns `created`, `updated`, and `destroyed` since that state, `newState` equal to the current session `state`, and `hasMoreChanges` false when the list fits in `maxChanges`. An IMAP append or a JMAP import is `created`. An IMAP flag change or a JMAP update, including a mailbox add or remove, is `updated`. An IMAP expunge, move, close, or mailbox delete that leaves another copy of the same email id is `updated`. One that removes the last copy, or a JMAP destroy, is `destroyed`. `sinceState` equal to the current state returns empty lists. An unknown `sinceState` is `cannotCalculateChanges`.

`Identity/get` returns one identity. Its `id` is `idn-` plus the account username and does not change. Its `email` is the account username. A `properties` list of `id` and `email` returns those two and no others. `id` is included even when `properties` omits it.

`EmailSubmission/set` `create` copies the stored RFC822 of `emailId` through the SMTP `DATA` accept path. `envelope.mailFrom.email` is the sender. Each `envelope.rcptTo` address is a recipient. A dataset account is appended to `INBOX` once. Any other recipient is accepted and not stored. `list-smtp` and `wait-smtp` count that submission the same way they count an SMTP `DATA`. The new id is returned under `created`. An unknown `emailId` is `notCreated` with type `notFound`. An empty `rcptTo` or a missing envelope is `notCreated` with type `invalidProperties`. Neither delivers. `onSuccessDestroyEmail` is a list of submission ids, or one id, including a creation id prefixed with `#`. Each id whose create succeeded destroys that submission's `emailId`. The same response then includes an `Email/set` whose `destroyed` lists those emails. Without `onSuccessDestroyEmail`, the email stays. `identityId` may be omitted; when set, it is that account's identity id.

`EmailSubmission/query` with `filter.emailIds` returns the ids of submissions created for those emails, in creation order, and no others. A filter without `emailIds` returns every submission for the account.

Any other method, including `Identity/set` and `EmailSubmission/get`, returns `unknownMethod`. `using` must list `urn:ietf:params:jmap:submission` or those three methods return `unknownMethod`.

## ManageSieve

`sieve_listen` speaks RFC 5804. The greeting is capability lines and then `OK`. It includes `IMPLEMENTATION`, `VERSION` `1.0`, `SASL` `PLAIN` and `CRAM-MD5`, and `SIEVE` including `fileinto` and `include`. `STARTTLS` is listed only when a certificate is loaded. `STARTTLS` returns `OK`, and the next greeting has no `STARTTLS`. `AUTHENTICATE "PLAIN"` with an initial response then works on that connection.

`AUTHENTICATE "PLAIN"` with an initial response, and `AUTHENTICATE "CRAM-MD5"`, accept a dataset account and return `NO` for a wrong password. Before that, `LISTSCRIPTS`, `GETSCRIPT`, `PUTSCRIPT`, `CHECKSCRIPT`, and `SETACTIVE` are `NO`.

`CHECKSCRIPT` and `PUTSCRIPT` accept a script only when every command is `require`, `keep`, `discard`, `stop`, `fileinto`, `redirect`, `if`, `elsif`, or `else`, in any case. `keep;` and `require ["fileinto"]; fileinto "INBOX";` are `OK`. A command ends with `;` or a brace block. A command that does not end with `;` or a brace block is `NO`. A command name outside that list is `NO`, including `this is not sieve`. Braces inside a quoted string do not count, and neither does a `#` comment. An unbalanced brace outside a quoted string is `NO`. An empty script is `NO`. `CHECKSCRIPT` of a script that passes returns an empty `OK` and stores nothing. That empty `OK` means no warnings. `PUTSCRIPT` of a script that passes stores the literal under that account and name. `PUTSCRIPT` of a script that fails is `NO` and does not store it, so `LISTSCRIPTS` does not include that name. The checker does not run the script. Delivery does not run a stored script. `GETSCRIPT` returns the stored bytes. An unknown name is `NO`. `LISTSCRIPTS` returns each stored name as a quoted string. The active name has `ACTIVE`. `SETACTIVE` of a stored name sets it. `SETACTIVE ""` clears it. `SETACTIVE` of an unknown name is `NO` and leaves the active name unchanged. `reset` and `set-dataset` drop every stored script.

## SMTP

`EHLO` lists `AUTH PLAIN LOGIN` when `smtp_auth_required` is true (the default), plus `OAUTHBEARER` and `XOAUTH2` when the personality lists those tokens, then `8BITMIME`, `PIPELINING`, `SMTPUTF8`, and `SIZE` plus the limit. `DSN` is listed only for a listener whose `dsn` is true. `STARTTLS` is listed only when a certificate is loaded and the connection is still cleartext. An implicit TLS listener never lists it. `STARTTLS` returns `220`, then both directions are TLS, and the next `EHLO` omits it. `STARTTLS` with an argument is `501`. A second `STARTTLS`, or `STARTTLS` with no certificate, is `454`.

`AUTH PLAIN` and `AUTH LOGIN` use the same dataset passwords as IMAP. While `smtp_auth_required` is true, `MAIL`, `RCPT`, and `DATA` before a successful `AUTH` are `530`. False omits `AUTH` from `EHLO` and accepts those three verbs with no AUTH. Any recipient is accepted. Nothing is relayed. The message is recorded on `list-smtp` and `wait-smtp` and is not delivered to an IMAP mailbox.

With AUTH required, `DATA` is stored once in the authenticated user's `INBOX` when at least one `RCPT TO` is a dataset account, as a bare name or `name@domain`. Any other recipient is accepted and does not by itself store the message. A failure report goes to the envelope sender's `INBOX`, using the local-part when that sender is a dataset account. There is no queue and no relay. A failure report is stored only when `inject-dsn` or a `bounce` fault asks for it. A success report is stored only when `inject-dsn` asks for `delivered`.

`MAIL FROM` accepts `BODY` (`7BIT`, `8BITMIME`, or `BINARYMIME`), `SIZE`, `RET=HDRS` or `RET=FULL`, `ENVID`, and `SMTPUTF8`. `RCPT TO` accepts `NOTIFY` (`SUCCESS`, `FAILURE`, `DELAY`, or `NEVER` alone) and `ORCPT`. Any other parameter is `501`. `SIZE` above `smtp_size` is `552 5.3.4` at `MAIL` and does not store.

## Log lines

One JSON object per line, append-only:

- `kind` — `command` (one client command) or `reply` (one server reply)
- `conn` — connection number, starting at 1
- `text` — the command or reply

`QUOTA`, when listed, answers `GETQUOTA` and `GETQUOTAROOT`. Before login both are tagged `NO`, and so is `SETQUOTA`. After login, without `QUOTA`, `GETQUOTA` and `GETQUOTAROOT` are tagged `BAD`. Without `QUOTASET`, `SETQUOTA` is tagged `BAD`. The one quota root is `ROOT`. Neither command requires a selected mailbox. `GETQUOTAROOT` takes one mailbox name. An existing mailbox returns `* QUOTAROOT` with that name in the same spelling `LIST` uses, then `ROOT`, and then one `* QUOTA ROOT` line. A missing mailbox is tagged `NO` and sends no quota line. `GETQUOTA ROOT` returns that `* QUOTA` line. `GETQUOTA` of any other name is tagged `NO`. A missing or extra argument is tagged `BAD`. The `* QUOTA` list always contains `STORAGE`, the sum of every message's RFC822 size in the shared store, converted to units of 1024 octets by rounding the total up. A 1-octet message uses 1. An empty store uses 0. A message marked `\Deleted` counts until `EXPUNGE`. `MESSAGE` is present only when `QUOTA=RES-MESSAGE` is listed, and it is the count of those same messages. `STORAGE` comes first. Annotation storage and mailbox count are reported only when the resource tokens below are listed. The starting `STORAGE` limit is 1048576. The starting `MESSAGE` limit is 1000000. Both live on the store, so a second connection sees a `SETQUOTA` from the first. `reset` and `set-dataset` restore both starting limits. `SETQUOTA ROOT` takes one parenthesized list of resource and number pairs. `STORAGE` and, when it is reported, `MESSAGE` change that limit. The untagged reply is the `* QUOTA` line with the new limits. An unknown resource, an empty list, a non-numeric limit, or `MESSAGE` when it is not reported is tagged `BAD`, and the limits stay. `SETQUOTA` of another root is tagged `NO`, and the limits stay. `cyrus-22.json` lists `QUOTA` immediately after `IMAP4rev1` and before `LITERAL+` on the pre-login and post-login lists, and not on the greeting. `cyrus-24.json` and `cyrus-25.json` list `QUOTA` immediately after `ENABLE` and before `NAMESPACE` on the pre-login list, and before `MAILBOX-REFERRALS` on the post-login list, and not on the greeting. `cyrus-36.json` lists `QUOTA` immediately after `QRESYNC` and before `SAVEDATE` on both, and not on the greeting. `cyrus-3124.json` and `cyrus-3137.json` list `QUOTA`, `QUOTA=RES-STORAGE`, `QUOTA=RES-MESSAGE`, and `QUOTASET` in that order, immediately after `QRESYNC` and before `REPLACE` on the pre-login list, and not on the greeting. On the post-login list those two files insert `QUOTA=RES-ANNOTATION-STORAGE` and `QUOTA=RES-MAILBOX`, in that order, after `QUOTA=RES-MESSAGE` and before `QUOTASET`. `sasl.json` lists those four on the post-login list only, in that order, immediately after `QRESYNC` and before `REPLACE`. `courier-50.json` and `courier-606.json` list `QUOTA` immediately after `SORT` and before `IDLE` on the greeting, pre-login, and post-login lists. `stalwart.json`, `stalwart-0155.json`, `stalwart-01625.json`, `stalwart-dev.json`, and `stalwart-oauth.json` list `QUOTA` then `QUOTA=RES-STORAGE` on the post-login list only, immediately after `PREVIEW`. `zimbra-883.json` lists `QUOTA` immediately after `QRESYNC` and before `SASL-IR` on the pre-login and post-login lists, and not on the greeting. No other lab personality lists `QUOTA`, `QUOTASET`, or a `QUOTA=RES-*` token. `QUOTA=RES-ANNOTATION-STORAGE` adds `ANNOTATION-STORAGE 0 <limit>` with default limit 0. `QUOTA=RES-MAILBOX` adds `MAILBOX <count> <limit>`, where count is the authenticated account's mailbox count and the default limit is 1000000. A reported limit of 0 does not reject `APPEND`. `cyrus-25.json` and `cyrus-36.json` list `X-QUOTA=STORAGE`, `X-QUOTA=MESSAGE`, `X-QUOTA=X-ANNOTATION-STORAGE`, and `X-QUOTA=X-NUM-FOLDERS` together on the post-login list, after `COMPRESS=DEFLATE` and before `IDLE`. `X-QUOTA=MESSAGE` adds `MESSAGE` even without `QUOTA=RES-MESSAGE`. `X-QUOTA=X-ANNOTATION-STORAGE` adds `X-ANNOTATION-STORAGE 0 <limit>`. `X-QUOTA=X-NUM-FOLDERS` adds `X-NUM-FOLDERS` with the same count and limit as `MAILBOX`. Annotation usage stays 0. Both `QUOTA=RES-` tokens leave `personalities/cyrus-3137.gaps.json`.

## ACL commands

`SETACL`, `DELETEACL`, `GETACL`, `LISTRIGHTS`, and `MYRIGHTS` are recognized on every personality, with or without a selected mailbox. `ACL` is not advertised. `RIGHTS=kxten` stays unimplemented and stays in `personalities/cyrus-3137.gaps.json`. The ACL verb `MYRIGHTS` stays `NO valid syntax not implemented`. `LIST-MYRIGHTS`, when listed, is a `LIST` return option: `LIST RETURN (MYRIGHTS)` sends `* MYRIGHTS <mailbox> lrswipkxtecda` after each `LIST` line for a mailbox the user owns. `LIST` without that return option sends no `MYRIGHTS` line. It is advertised post-login only: `cyrus-25.json` after `LIST-STATUS` and before `WITHIN`; `cyrus-36.json` after `LIST-EXTENDED` and before `LIST-STATUS`; `cyrus-3124.json` and `cyrus-3137.json` after `LIST-EXTENDED` and before `LIST-STATUS`. No personality file lists `ACL`.

Before login, each command is tagged `NO` `must authenticate first`, including a command with the wrong number of arguments.

After login, a command whose arguments are valid is tagged `NO` `valid syntax not implemented`. That text is exact. There is no response code. There is no untagged `ACL`, `LISTRIGHTS`, or `MYRIGHTS` line. Nothing is stored: messages, flags, and mailboxes stay as they were.

Each argument is an astring. `SETACL` takes three, `DELETEACL` two, `GETACL` one, `LISTRIGHTS` two, and `MYRIGHTS` one. A missing argument, an extra argument, or a parenthesis is tagged `BAD`. The mailbox astring may name a mailbox that does not exist. That is still the `NO` phrase. There is no `TRYCREATE` and no mailbox lookup.

An identifier is a non-empty astring, including `anyone` and an identifier that starts with `-`. An empty quoted string or an empty literal is tagged `BAD`. Identifiers are not rewritten.

`SETACL`'s third astring is an optional leading `+` or `-`, then zero or more of `l`, `r`, `s`, `w`, `i`, `p`, `k`, `x`, `t`, `e`, `a`, `c`, and `d`. The empty string, `+`, and `-` are valid. A repeated letter is valid. Any other character, a `+` or `-` after the first character, an uppercase letter, a digit, or `n` is tagged `BAD`.

`UID` plus any of the five names is tagged `BAD` `syntax error` and does not return the stub phrase.

## FILTER command

`FILTER` and `UID FILTER` are the Sieve command from draft-bosch-imap-filter-sieve-00. They are recognized on every personality. `FILTER=SIEVE` is not advertised. RFC 5466 `FILTERS` is not implemented. No personality file lists `FILTER=SIEVE`. ManageSieve script storage is unchanged.

With no mailbox selected, before or after login, `FILTER` and `UID FILTER` are tagged `NO` `FILTER not selected`. The arguments are not checked.

With a mailbox selected, a command whose arguments are valid is tagged `NO` `not implemented`. That text is exact. There is no response code. There is no untagged `FILTER` or `FILTERED` line. No script runs. The search is not run. Messages, flags, mailboxes, and ManageSieve scripts stay as they were. `UID FILTER` uses that same phrase and does not report UIDs.

The spec words are case-insensitive. The spec is one of `SIEVE DELIVERY`, `SIEVE PERSONAL` and a non-empty astring, `SIEVE GLOBAL` and a non-empty astring, or `SIEVE SCRIPT` and an astring. The script astring may be empty and may be text that is not a Sieve script. The name is not looked up. The script text is not parsed. Any other spec, a missing spec, or an empty `PERSONAL` or `GLOBAL` name is tagged `BAD`. That text is not `not implemented`.

After the spec, an optional `CHARSET` astring and one or more search keys follow. `CHARSET` and the keys are accepted exactly when `SEARCH` on this connection would accept them, including the capability gates `SEARCH` already applies. A key or charset `SEARCH` would reject is tagged `BAD`. Zero search keys is tagged `BAD`. A `RETURN` parenthesized list is tagged `BAD`.

## COMPARATOR and URLAUTH commands

`COMPARATOR`, `GENURLAUTH`, `URLFETCH`, and `RESETKEY` are recognized on every personality. `URLAUTH` and `URLAUTH=BINARY` are in `implementedCaps`. `I18NLEVEL=1` is not. `advertiseList` drops `I18NLEVEL=1` and `URL-PARTIAL` by name after the implemented-capability check. `ENABLE I18NLEVEL=1` adds nothing to `* ENABLED`. `URL-PARTIAL` stays unimplemented. `personalities/cyrus-3137.gaps.json` keeps `URL-PARTIAL` and does not keep `URLAUTH` or `URLAUTH=BINARY`. Those two tokens are advertised post-login only: `cyrus-24.json` after `XLIST` and before `COMPRESS=DEFLATE`; `cyrus-25.json` after `CREATE-SPECIAL-USE` and before `COMPRESS=DEFLATE`; `cyrus-36.json`, `cyrus-3124.json`, and `cyrus-3137.json` after `UNSELECT` and before `WITHIN`.

`COMPARATOR` before login is tagged `NO` `must authenticate first`, including a command with invalid arguments. After login, one astring, or a parenthesized list of one or more astrings, is tagged `NO` `not implemented`. That text is exact. There is no response code and no untagged `COMPARATOR` line. `SORT` and `SEARCH` keep today's comparison. An empty list, a missing argument, or a parenthesis that does not wrap astrings is tagged `BAD`. That text is not `not implemented`.

`GENURLAUTH` and `RESETKEY` require login. Before login each is tagged `NO` `must authenticate first`, including a command with invalid arguments. `URLFETCH` does not require login.

Valid `GENURLAUTH` is one or more pairs of a url-rump and the atom `INTERNAL`, `AUTHENTICATED`, or `ANONYMOUS`. A quoted mechanism is tagged `BAD`. A url-rump contains `imap://` and `/;UID=` followed by a non-zero number. Each pair returns one `* GENURLAUTH` line whose URL ends with `;URLAUTH=` in lowercase, the mechanism, a colon, and a token, then `OK GENURLAUTH completed`. The token is bound to the rump, the user, and the mailbox key. A missing pair or a rump without those two pieces is tagged `BAD` `GENURLAUTH syntax`.

Valid `URLFETCH` is one or more URLs that each contain those two pieces and `;URLAUTH=` followed by a non-empty atom. A URL with no section returns the stored RFC822 bytes. A URL with `;section=` or `;SECTION=` returns that still-encoded body part. An unknown URL, a bad token, a reset key, or a missing part returns `NIL`. The tagged result is `OK URLFETCH completed`. With `URLAUTH=BINARY` advertised, `URLFETCH` of a parenthesized URL and the atom `BINARY` returns `* URLFETCH` and `(BINARY` plus the decoded section. A NUL in that data is literal8. An unknown transfer encoding is `(BINARY NIL)`. A URL without `;URLAUTH=` is tagged `BAD`.

Valid `RESETKEY` is no argument, or one mailbox astring, including a name that does not exist, and is `OK RESETKEY completed`. No argument resets every mailbox in every tree. One mailbox resets that mailbox. Later fetches of the affected URLs are `NIL`. A second argument is tagged `BAD` `RESETKEY syntax`. Invalid arguments are tagged `BAD`. That text is not `not implemented`. `UID` plus any of the four names is tagged `BAD` `syntax error`.

## SASL

`AUTHENTICATE` mechanisms this binary implements: `PLAIN`, `LOGIN`, `CRAM-MD5`, `SCRAM-SHA-1`, `SCRAM-SHA-256`, `SCRAM-SHA-1-PLUS`, `SCRAM-SHA-256-PLUS`, `EXTERNAL`, `OAUTHBEARER`, and `XOAUTH2`. A mechanism is advertised only when the personality lists `AUTH=<name>`, and `AUTHENTICATE` of a mechanism that is not listed fails. `DIGEST-MD5` is not implemented and is not advertised.

`LOGIN` asks for the username and then the password. An initial response, when the client sends one, is the username.

`CRAM-MD5` checks HMAC-MD5 of the server challenge against the dataset password.

`SCRAM-SHA-1` and `SCRAM-SHA-256` check the dataset password over the four SCRAM messages. A wrong password or a bad client proof fails. A client `*` cancels. The `-PLUS` forms require TLS and channel binding `tls-unique` or `tls-exporter`, and fail when the binding does not match the connection. Either `-PLUS` mechanism on a cleartext connection fails.

`EXTERNAL` succeeds when the client certificate was verified and an email SAN, a DNS SAN, or the subject CN equals an account username, and the authorization identity is empty or that same username. No client certificate, or a name that matches no account, fails. `PLAIN` still works on a listener that accepts a client certificate.

## Dataset

Directory: `datasets/demo/`

`dataset.json` keys:

- `accounts` — objects with `username` and `password`
- `mailboxes` — objects with `name`, optional `uid_validity`, optional `messages`, optional `generated`, optional `special_use`
- `messages` — objects with `file` (path relative to the dataset directory), `flags` (IMAP flag names), and `internal_date` (`02-Jan-2006 15:04:05 -0700`)
- `generated` — `count`, `seed`, `from`, `to`, `subject`, `start` (same date form as `internal_date`), `step_seconds`
- `special_use` — optional array of special-use flags on that mailbox: `\All`, `\Archive`, `\Drafts`, `\Flagged`, `\Junk`, `\Sent`, `\Trash`. A flag belongs to at most one mailbox.

An overlaid message is stored from its file. A generated mailbox keeps a header index only (`from`, `to`, `subject`, `date`, `size`, `flags`). Its RFC822 bytes are produced from the seed and the generation id when a command needs them, and are not kept on the message.

## Control socket

One JSON object per line in, one JSON object per line out: `{"ok":true,...}` or `{"ok":false,"error":"..."}`.

Ops: `status`, `reset`, `set-personality`, `set-dataset`, `disconnect`, `inject`, `arm-inject`, `list-mail`, `fetch-mail`, `accounts`, `freeze-clock`, `thaw-clock`, `arm-fault`, `clear-faults`, `inject-dsn`, `list-smtp`, `wait-smtp`, `bye`, `set-login-disabled`, `create-mailbox`, `set-auth-policy`, `clear-auth-policy`, `reload-cert`, `issue`, `list-tokens`, `revoke`, `auth-log`, `set-referral`, `clear-referral`, `register-client`. `status` includes `listen`, `implicit_tls_listen`, `control`, `smtp`, `smtp_listeners`, `smtp_tls`, `smtp_tls_listeners`, `jmap`, `jmap_tls`, `sieve`, `oauth`, and `oauth_tls`. `smtp` is the first cleartext SMTP bind, or `""` when none is up. `smtp_listeners` lists every cleartext SMTP bind. `smtp_tls` is the first implicit SMTP TLS bind, or `""`. `smtp_tls_listeners` lists every one. `jmap`, `jmap_tls`, and `sieve` are the bound `host:port`, or `""` when that listener is not up.

`bye` takes optional `conn` and optional `text` (default `Server logging out`). Each matched IMAP connection, including one inside `IDLE` after `+ idling` and before `DONE`, is sent `* BYE` plus that text, flushed, and closed. There is no tagged IDLE reply. Omitted `conn`, or `0`, matches every IMAP connection.

Request fields: `path`, `conn`, `mailbox`, `user`, `username`, `password`, `raw`, `uid`, `time`, `id`, `command`, `times`, `do`, `delay_ms`, `bytes`, `text`, `count`, `offset`, `tag`, `order`, `timeout_ms`, `status`, `code`, `proto`, `size`, `after`, `value`, `done`, `total`, `name`, `name_b64`, `fail_delay_ms`, `lockout_after`, `lockout_ms`, `cert_file`, `key_file`, `to`, `recipient`, `envid`.

`set-login-disabled` takes `value` true or false. True forces `LOGINDISABLED` and the `LOGIN` refusal on cleartext even when the personality omits the token, including a cleartext process with no certificate. False forces the token off and allows `LOGIN` on cleartext even when the personality lists it. Omitted, the personality list and the certificate filter decide. The override is not a fault.

`create-mailbox` takes `name` or `name_b64`, and rejects a request that has neither. A request that has both is `bad name`. Optional `user` matches `inject`: a non-empty user must name an account, and the mailbox is created in that account's tree. An omitted user uses the first dataset account. `name_b64` is standard base64 of the raw mailbox bytes and may be invalid UTF-8. The store keeps those bytes. `LIST`, `LSUB`, and `STATUS` emit them. A name that is not an atom, including any invalid UTF-8, is an IMAP literal. `SELECT` of that same byte string selects the mailbox, before and after `ENABLE UTF8=ACCEPT`. The server does not replace the bytes and does not panic.

`set-auth-policy` takes optional `fail_delay_ms`, `lockout_after`, and `lockout_ms`. Omitted or `0` turns that field off. All zeros, and `clear-auth-policy`, restore instant failures and clear the failure counts. A failed `LOGIN` or `AUTHENTICATE` still ends `NO [AUTHENTICATIONFAILED]`, after a wall-clock sleep of `fail_delay_ms`. `NO [PRIVACYREQUIRED]` is not a failure: it does not sleep and it does not count. Failures count per username, and per connection when the username is empty. After `lockout_after` failures, further attempts for that username are `NO [UNAVAILABLE] Authentication temporarily locked` until the lockout ends. A successful login clears that username's count. When `freeze-clock` is set, the deadline is that frozen time plus `lockout_ms`, and a later `freeze-clock` at or after the deadline ends the lock. With no frozen clock, the deadline is wall time. `reset` and `set-dataset` do not clear the policy.

`reload-cert` takes optional `cert_file` and `key_file`, both or neither. One without the other is `missing field`. Neither re-reads the configured paths. A pair that does not load returns `ok` false and keeps the previous certificate. The new certificate is used for the next handshake on IMAP implicit TLS, IMAP `STARTTLS`, SMTP `STARTTLS`, SMTP implicit TLS, JMAP TLS, and ManageSieve `STARTTLS`. A connection that has already finished TLS keeps the old certificate. An armed `expired` or `self_signed` fault still wins for a handshake it matches. Loading a certificate when none was loaded makes `LOGINDISABLED` follow the filter already in `advertiseList`.

`inject-dsn` takes `code` of `delivered` or `failed`. Optional `to` is the dataset account whose `INBOX` receives the report. Omitted, that account is the envelope sender of the latest accepted SMTP message, and only when that sender is a dataset account. Optional `recipient` and `envid` are copied into the report. Optional `raw` is stored as the message bytes. Without `raw`, the message is a `multipart/report` whose delivery-status part is `message/delivery-status`. A bad `code`, or no account to store into, is `missing field` or `no such account`.

`list-smtp` returns `messages`. Each item has `from` and `recipients`, plus `ret`, `envid`, `smtputf8`, and `size` when `MAIL FROM` sent those parameters. `size` is the declared `SIZE`, not the stored length. A recipient has `address` and `result` (`delivered` or `discarded`), plus `notify` and `orcpt` when `RCPT TO` sent them. A delivered recipient was appended to `INBOX`. A discarded recipient was accepted and not stored. `wait-smtp` takes `count`. Zero returns immediately. A positive count also takes `timeout_ms` and waits until that many SMTP messages have been accepted since the call. If `timeout_ms` passes first, the reply is `ok` false.

Fault `do` names: `close`, `rst`, `half_close`, `silent`, `delay`, `drip`, `truncate`, `raw`, `bad_literal`, `flood`, `split`, `coalesce`, `wrong_tag`, `unsolicited`, `reorder`, `mid`, `fetch_order`, `tag_first`, `mutate`, `wrong_name`, `expired`, `self_signed`, `reply`, `bye`, `idle_burst`, `drop_literal`, `rst_literal`, `overquota`, `expunge_mid`, `inprogress`, `drop_after_354`, `bounce`, `unauthorized`, `server_fail`, `drop_eventsource`, `expired_token`, `wrong_scope`, `revoked_refresh`, `invalid_grant`, `slow_token`. `expired_token` is distinct from TLS `expired`. It treats a stored token as expired, leaves it stored, and wins over a frozen clock that has not reached expiry. `wrong_scope` rejects a token whose stored scopes would otherwise pass. `revoked_refresh` fails the refresh grant and leaves the token listed. `invalid_grant` makes the next N code or refresh exchanges return `invalid_grant`. `slow_token` delays `POST /token` by at least `delay_ms`. Those five are not generic reply faults. An unknown `do` stays `unknown fault`.

`times` and `conn` match the other faults. Omitted or `0` matches every time and every connection of that protocol. `times` N matches the Nth time only. An unknown `do` or `proto` is `unknown fault`. A missing required field is `missing field`. Optional `proto` defaults to `imap`.

`reply` requires `command`. For IMAP, it also requires `status` of `OK`, `NO`, or `BAD`, and takes optional `code` and `text`. The tagged line is `tag STATUS [CODE] text` when those fields are set. The command does not run. `SELECT` does not select. `APPEND` does not store. For `proto` `smtp`, `reply` requires a numeric `code` from 200 to 599 and takes optional `text`. That reply is sent, the SMTP command does not run, and nothing is stored. A spent fault lets the next command run.

`bye` requires `command`. Optional `text` defaults to `Server logging out`. When that command runs, the server sends `* BYE` plus that text, flushes, and closes. There is no tagged reply for that command.

`idle_burst` requires `command` `IDLE` and the same `text` line payload as `unsolicited`. `+ idling` and those lines are one socket write, with no flush between them. `DONE` is still a tagged OK.

`drop_literal` and `rst_literal` require `command` and `bytes` of 0 or more. After the literal header is accepted, and after `+ go ahead` when the literal is synchronizing, the server reads that many body octets and then closes or resets. The message is not stored. `LITERAL+` and a synchronizing literal both work.

`bad_literal` with no `size` still advertises `n+1`. With `size`, the braces advertise that exact number, including a value larger than the payload. The payload bytes are unchanged. A `+` stays when the literal had one.

`overquota` requires `command`. Optional `proto` defaults to `imap`. IMAP commands that store mail (`APPEND`, a multi-message `APPEND`, `COPY`, `MOVE`, `XMOVE`, `REPLACE`, and the `UID` forms) are tagged `NO [OVERQUOTA]` and store nothing. A move does not expunge the source. `REPLACE` does not expunge the old message and does not store the new one. SMTP `MAIL`, `RCPT`, or `DATA` is `552 5.2.2` and `list-smtp` gains no message. JMAP `Email/import` or `Email/set` returns `overQuota` and stores nothing. `GETQUOTA`, `GETQUOTAROOT`, and `SETQUOTA` are unchanged. An IMAP fault does not match an SMTP command.

`proto` `smtp` also applies `close`, `rst`, `half_close`, `silent`, `delay`, `raw`, `reply`, and `drop_after_354` to the SMTP verb in `command` (`EHLO`, `MAIL`, `RCPT`, `DATA`, `AUTH`, `STARTTLS`, and any other verb named there). `conn` omitted or `0` matches every SMTP connection. `close`, `rst`, and `half_close` drop the connection the same way they do for IMAP. `silent` runs the command and writes nothing. `delay` waits `delay_ms` and then writes the real reply. `raw` runs the command and writes `text` in place of the reply. `drop_after_354` is `DATA` only: the server sends `354`, reads optional `bytes`, then closes, and does not store. `bounce` is `DATA` only. The data is accepted with `250`. The server then stores one failure report for each recipient whose `NOTIFY` contains `FAILURE`, or for every recipient when `NOTIFY` was omitted, in the envelope sender's `INBOX` when that sender is a dataset account. A recipient that was not accepted, and a recipient whose `NOTIFY` does not ask for failure, does not get a report. A success report is not sent for `bounce`.

`proto` `sieve` accepts only `reply`. Any other `do` is `unknown fault`. `reply` requires `command` of `CHECKSCRIPT` or `PUTSCRIPT`. It does not take `status`. A script the checker would accept is `NO`, and `PUTSCRIPT` does not store it. `times` and `conn` match the other faults. `conn` is the ManageSieve connection number.

`proto` `jmap` accepts `unauthorized`, `server_fail`, and `drop_eventsource`. Those three are `unknown fault` on `imap` and `smtp`. `command` may be omitted. Omitted, it matches every API, upload, download, and event-source request. When set, it is `api`, `upload`, `download`, `eventsource`, or a method name such as `Email/get`. `times` and `conn` match the other faults. `conn` is the JMAP request number, starting at 1 for each of those requests. Omitted or `0` matches every request. `GET /.well-known/jmap` is not a match.

`unauthorized` makes the next matched API, upload, download, or event-source request HTTP `401`. The request does not run. `server_fail` makes upload, download, and the event source HTTP `500`. A matched `/jmap/` method returns `serverFail` and does not run. When `command` is omitted or `api`, every method in that request returns `serverFail`. `drop_eventsource` closes an event stream that is already open immediately. A stream opened while the fault matches stays up through its first event and then closes.

`inprogress` requires `command` of `SEARCH`, `ESEARCH`, or `SORT`. `UID SEARCH`, `UID ESEARCH`, and `UID SORT` match those commands. Optional `delay_ms` waits that many wall-clock milliseconds between the progress lines. A negative `delay_ms` is `missing field`. Optional `count` defaults to 2. A negative `count` is `missing field`. Optional `done` and `total` are JSON numbers; omitted, or JSON null, the line uses `NIL`. Any other `done` or `total` is `missing field`. When the connection advertises `INPROGRESS`, the server sends that many `* OK [INPROGRESS (tag done total)]` lines, then the command's unchanged result and tagged OK. A personality that does not advertise the token sends none of those lines and the command still succeeds. With the token advertised and no fault armed, `SEARCH`, `UID SEARCH`, `ESEARCH`, `SORT`, and `UID SORT` send no `INPROGRESS` line.

`expunge_mid` requires `command` and `uid`, and takes optional `after` (default 1; `0` means before the first FETCH line). The UID is expunged in the selected mailbox through the same path as `EXPUNGE`, including the JMAP expunge record, and the notice is flushed before the tagged reply. A `CONTEXT=SEARCH` context that contained that UID sends `REMOVEFROM` before the notice. On `FETCH` or `UID FETCH`, `after` N places that notice after N fetch lines and before the rest. A UID that is not in the mailbox returns `ok` false and changes nothing. With `UIDONLY` or `QRESYNC` enabled the notice is `VANISHED`. With `UIDONLY` enabled later lines are `UIDFETCH`. Otherwise the notice is `* seq EXPUNGE` and later fetch lines use the corrected sequence numbers. `FETCH` also flushes pending events between fetch lines, so a second connection's `EXPUNGE` can land in that same gap.

## Accounts, referrals, and OAuth

The first dataset account keeps the mailboxes and messages in the dataset. Every other dataset account, and every account added through `accounts`, starts with an empty subscribed `INBOX`. A mailbox object may set `account`. An omitted `subscriptions` list, or a list that omits `INBOX`, leaves `INBOX` subscribed. `inject` without `user` uses the first dataset account. `inject` accepts optional `flags` and `internal_date`. Omitted flags are empty. Omitted date uses the frozen clock, or the wall clock. `seq` together with `new_uidvalidity` sets that UIDVALIDITY and renumbers messages so the new message occupies `seq`. Existing messages keep their JMAP ids. `seq` without `new_uidvalidity`, or a `seq` outside `1` through one past the end, is `missing field`. The reply `uid` is the assigned UID. A selected connection whose mailbox is renumbered receives `* OK [CLOSED] UIDVALIDITY changed` and returns to authenticated with no mailbox selected. `arm-inject` stores one counted inject with `command`, optional `conn`, `times` (omitted means 1; 0 means every time), and the same mailbox fields as `inject`. The message is in the store before that command's untagged replies.

A name under an other-user prefix (`Other Users/` on cyrus-3124 and cyrus-3137, `user.` on cyrus-22 and cyrus-24, `user/` on cyrus-25 and cyrus-36, `~` on uwimap) takes the next component as the account and resolves the rest in that account's tree. A missing account, or a remainder that is not a mailbox, is `NO` with `no such mailbox` on `SELECT`, `EXAMINE`, and `STATUS`. The prefix plus an account and an empty remainder is listed with `\HasChildren` and the personality's `\Noselect` or `\NoSelect` spelling when that account has mailboxes. `SELECT` or `EXAMINE` of that node is no such mailbox. A non-empty shared prefix (`Shared Folders/` on cyrus-3124 and cyrus-3137, `#shared.` and `shared.` on Courier, `#shared/`, `#ftp/`, `#news.`, and `#public/` on uwimap) uses one shared tree that starts empty and is visible to every authenticated account. An empty shared prefix is not that tree. On dovecot-245 and dovecot-dev, uwimap, and both Courier files, a missing parent of a stored mailbox is listed and is not selectable. Other servers do not synthesize parents. `CREATE` of that name stores a real mailbox.

`set-referral` takes `kind` `login` or `mailbox`, `url`, optional `mailbox`, and optional `conn`. `clear-referral` drops it. `kind=login` makes `LOGIN` and `AUTHENTICATE` return `NO [REFERRAL <url>] login referral` before the password check, and the lockout counter does not change. `kind=mailbox` makes `SELECT`, `EXAMINE`, `CREATE`, `DELETE`, and `RENAME` of that mailbox return `NO [REFERRAL <url>] mailbox referral`. The referral is honored even when the capability is not advertised. `LOGIN-REFERRALS` is advertised on the Dovecot files and on uwimap where those files list it. `MAILBOX-REFERRALS` is advertised on cyrus-24 and cyrus-25 after `QUOTA` and before `NAMESPACE`, on cyrus-3124 and cyrus-3137 after `LITERAL+` and before `MOVE`, on cyrus-36 after `LIST-STATUS` and before `MOVE`, and on uwimap post-login after `CHILDREN` and before `BINARY`. `cyrus-22.json` lists `IMAP4` then `IMAP4rev1` on the pre-login and post-login lists. The greeting stays an empty capability list. Commands stay IMAP4rev1. `X-CREATEDMODSEQ`, when listed, is the modseq stored at create time. Dataset mailboxes use 1. `STATUS` and `FETCH` of `X-CREATEDMODSEQ` return that number. cyrus-3124, cyrus-3137, and cyrus-36 list it on the post-login list immediately after `THREAD=REFS`.

`issue` takes `username` or `user`, optional `client_id`, `scopes`, `access_seconds`, and `refresh_seconds`. The reply returns `id`, `access_token`, `refresh_token`, `token_type`, `expires_in`, and `scope` once. `list-tokens` omits secrets. `revoke` takes `token_id`. Tokens live on the server, so `reset` and `set-dataset` do not wipe them. A token for a removed user fails the user check. No scope allows IMAP, SMTP, and JMAP. A listed scope requires `imap`, `smtp`, or `jmap` for that protocol. `freeze-clock` expires a short token. `auth-log` returns attempts with time, proto, mechanism, username or client id, and result, and omits raw secrets. Protos include `authorize`, `token`, and `revoke`.

`personalities/stalwart-oauth.json` matches `stalwart.json` and adds `AUTH=OAUTHBEARER` and `AUTH=XOAUTH2` beside `AUTH=PLAIN` on the greeting and pre-login lists only. The post-login list matches `stalwart.json`. A personality that does not list the mechanism returns IMAP `NO AUTHENTICATE mechanism not available` and SMTP `504 5.5.4 unrecognized authentication type`. IMAP and SMTP accept those mechanisms when listed, including SASL-IR. `=` is the empty initial response. OAUTHBEARER is `n,a=<user>,` then the host, port, and `auth=Bearer` token fields. An omitted or empty `a=` uses the bound user. A non-empty `a=` must equal that user. XOAUTH2 is `user=<user>` and `auth=Bearer`, and `user=` must equal the bound user. Success authenticates that dataset user. `store.check` stays the password path. An invalid, expired, revoked, or wrong-scope token gets a continue whose payload is base64 JSON, then the client completion, then tagged `NO` on IMAP and `535` on SMTP. Bearer failures do not change the `set-auth-policy` counter. `UNAUTHENTICATE` clears the session and leaves the token valid. With `set-login-disabled` true, `LOGIN` is `NO [PRIVACYREQUIRED] LOGIN disabled` and bearer `AUTHENTICATE` still succeeds.

The OAuth listener routes are `GET /.well-known/oauth-authorization-server`, `GET /.well-known/openid-configuration` with the same metadata, `GET /authorize` only, `POST /token`, and `POST /revoke`. Issuer URLs use the bound host and port. Metadata lists `issuer`, `authorization_endpoint`, `token_endpoint`, `revocation_endpoint`, `response_types_supported` `["code"]`, grant types `authorization_code` and `refresh_token`, `code_challenge_methods_supported` `["S256"]`, and `token_endpoint_auth_methods_supported` exactly `["none", "client_secret_post"]`. There is no userinfo and no id_token. Authorize requires `login_hint` or `username`. When both are present they name the same dataset user. A mismatch or a missing user is `invalid_request` on the redirect. An unknown scope is `invalid_scope` on the redirect. Omitted scope means all three protocols. `response_type=code`, a registered client, an exact `redirect_uri`, `state`, and PKCE S256 are required. Success is 302 with `code` and `state`. An unregistered redirect URI is HTTP 400. Codes are single-use. Confidential clients use `client_secret_post` only. `register-client` takes `id`, `secret`, and `redirect_uris`. A code-issued token works on IMAP OAUTHBEARER, SMTP AUTH, and JMAP Bearer.

## Probe

`cyrusprobe` is a separate command from `fakeimap`. `make` builds it with `go build -tags probe -o cyrusprobe .` after `go test`. `make` does not start Docker.

Run: `cyrusprobe [-gaps gaps.json] operator.json`. The operator file is JSON. The example `cyrusprobe.example.json` has an empty password. A filled file is `cyrusprobe.local.json` (gitignored).

Operator keys:

- `host` — IMAP host
- `port` — IMAP port
- `tls` — `none`, `starttls`, or `implicit`
- `username`
- `password` — empty in the example
- `personality` — personality JSON file used for the local server

The command runs one script against that server and against a local `fakeimap` using the personality file, then prints a normalized diff. `-gaps` writes capabilities the remote advertised that this binary does not implement. `commands` in that file is the unimplemented commands the script saw. Tags, UIDs, `UIDVALIDITY`, `UIDNEXT`, `INTERNALDATE`, message counts the script caused, and timestamps are not differences. Capability sets in the diff keep only capabilities this binary implements.

The script reads the greeting. When that greeting advertises `LOGINDISABLED` and the connection is still cleartext, it sends `STARTTLS` and upgrades before `LOGIN`. The cleanup login does the same. It then sends `CAPABILITY`, `LOGIN`, `CAPABILITY`, `NAMESPACE`, `CREATE` a fresh mailbox, `SELECT` it, `APPEND` one fixed message, `FETCH` `FLAGS UID INTERNALDATE RFC822.SIZE ENVELOPE BODYSTRUCTURE BODY.PEEK[HEADER]`, `FETCH` `BODY[TEXT]`, `STORE` a flag, `CREATE` a second fresh mailbox, `COPY` into it, `SELECT` that mailbox, `MOVE` the message back, `SEARCH ALL`, `LIST` the probe mailboxes, `LOGOUT`. It then logs in again and deletes the mailboxes it created.

`cyrusprobe -condstore` runs a second script for `CONDSTORE` and `QRESYNC`: enable them, `CHANGEDSINCE`, `UNCHANGEDSINCE`, an unsolicited flag update, `VANISHED` versus `EXPUNGE`, and `SELECT QRESYNC`. The diff compares response kinds. It does not replace the first script. `make` does not run it against Docker.

`cyrusprobe -list` runs a third script for extended `LIST` and `CREATE` with `USE`. The diff compares response kinds, not counts. It does not replace the first two scripts. `make` does not run it against Docker.

`cyrusprobe -esearch` runs a further script for `ESEARCH` and a positive `PARTIAL` window. The diff compares response kinds. It does not replace the earlier scripts. `make` does not run it against Docker.

`cyrusprobe -compress` runs a further script that sends `COMPRESS DEFLATE` and decompresses both directions before it compares response kinds. It does not replace the earlier scripts. `make` does not run it against Docker.

`cyrusprobe -sort` runs a further script for `SORT` and one positive `ESORT` `PARTIAL` window. The messages it appends differ in `FROM`, `DATE`, `SUBJECT`, and `SIZE`, and one command uses `REVERSE`. The diff compares response kinds. It does not replace the earlier scripts. `make` does not run it against Docker.

`cyrusprobe -display` runs a further script for one `UID SORT (DISPLAYFROM)` whose display name sorts differently from the address. The diff compares response kinds. It does not replace the earlier scripts. `make` does not run it against Docker.

`cyrusprobe -thread` runs a further script for one `UID THREAD REFERENCES` and one `UID THREAD ORDEREDSUBJECT`. The messages have distinct subjects and one reply whose parent is in the set. The diff compares thread shape, with message numbers folded to `N`. It does not replace the earlier scripts. `make` does not run it against Docker.

`cyrusprobe -binary` runs a further script for one `BINARY.PEEK[1]` of a `base64` part and one `<0.5>` partial of that part. The diff compares response kinds, including the `BINARY` item token. It does not compare the literal bytes. It does not replace the earlier scripts. `make` does not run it against Docker.

`cyrusprobe -fuzzy` runs a further script for one `UID SEARCH RETURN (COUNT) FUZZY TEXT` of a word in an appended message. The diff compares response kinds. `COUNT` is recorded and the number is not. It does not replace the earlier scripts. `make` does not run it against Docker.

`cyrusprobe -multisearch` runs a further script for one `ESEARCH IN (subtree <fresh>) RETURN (ALL) TEXT` whose word is in one child of that mailbox. The diff compares response kinds. The correlator is skipped and `UID ALL` is recorded. It does not replace the earlier scripts. `make` does not run it against Docker.

`cyrusprobe -preview` runs a further script for one `FETCH` of `PREVIEW`. The diff compares response kinds. It does not replace the earlier scripts. `make` does not run it against Docker.
